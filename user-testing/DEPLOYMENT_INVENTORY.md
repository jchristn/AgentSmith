# Deployment inventory for simulated user testing

Hugo has three supported container deployment paths: Docker Compose, Kubernetes, and minikube (D-045). Use this inventory when preparing sessions under the family `SIMULATED_USER_TESTING.md` requirements. It describes required coverage, not a completed session or evidence of a passing deployment. Source builds are development workflows, not another deployment path.

| Path | Installation entry points | Variants to cover | Documentation |
|---|---|---|---|
| Docker Compose | `docker/start.sh` and `start.bat`; explicit `docker compose` commands | Default SQLite; `postgres` profile; generated keys; dashboard plus observability; optional `compose.docker-socket.yaml` with a disposable daemon; `docker/factory/compose.yaml` and its reset scripts for the seeded demo | [Docker](../docs/DOCKER.md), [factory](../docs/FACTORY.md), [image README](../DOCKERHUB_README.md) |
| Kubernetes | `k8s/scripts/generate-secrets`, `deploy`, `wait-rollout`, `smoke-test`, and `port-forward` (`.sh` and `.bat`); direct Kustomize or Helm | `k8s/base`; `k8s/overlays/k3s`; `k8s/overlays/production` with external PostgreSQL and TLS secrets; optional PostgreSQL, observability, and ingress components; `k8s/helm/hugo` with defaults and `values-k3s`, `values-production`, and `values-minikube` | [Kubernetes](../docs/KUBERNETES.md), [assets](../k8s/README.md) |
| minikube | `minikube/scripts/start`, `deploy`, `smoke-test`, and `port-forward` (`.sh` and `.bat`) | `minikube/overlay`; published image pulls, `--load`, `--build`; SQLite and `--with postgres`; `--with observability` and both components together; ingress and local port-forwards | [minikube](../minikube/README.md), [Kubernetes](../docs/KUBERNETES.md) |

For each path, begin with an isolated clean instance and record the checkout, dirty state, platform, tool versions, image digests, ports, settings, and setup time in the dated session report. Follow the documented commands literally, recording deviations. Exercise first sign-in and the advisory password prompt, dashboard chat with a test model, REST and real MCP client access, connectors, and Grafana. Verify that an update preserves users, profiles, secrets, and history; back up and restore the database together with its encryption key; then verify reset removes the isolated data and teardown leaves no test resources. Record a reason for every variant or Windows script not exercised.

Kubernetes and minikube also need checks for one server replica with Recreate, readiness, ingress streaming, secrets created before pods, PostgreSQL initialization, and the read-only settings file limitation. Cover both Kustomize and Helm installations in the session matrix rather than treating a successful render as a live deployment. Never test a host Docker socket against a shared daemon; use a disposable target for the optional connector override.

Static validation runs separately: `.github/workflows/k8s.yaml` runs on every push and pull request and invokes `k8s/tests/check-render.sh`. That script checks mirrored configuration, renders the base and overlay/component combinations plus their Helm equivalents, rejects multiple server replicas, validates Kubernetes schemas with kubeconform, and compares the resulting objects. Compose configuration can be validated with `docker compose config --quiet` without starting containers. Neither check replaces the live journeys required by P12.13 or P16.9.

Keep raw captures under ignored `user-testing/evidence/` and write dated reports as `user-testing/YYYY-MM-DD-label.md`. List findings, coverage gaps, and cleanup explicitly; an inventory row alone never means a test passed.
