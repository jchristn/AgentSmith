# Internationalization

Hugo's dashboard speaks twelve languages; the server speaks in codes. That split is deliberate. Everything an operator reads in the dashboard is translated in the browser from catalogs, and everything the server returns that a person might see carries a stable machine code the dashboard can look up. Nothing on the server decides what language you get.

The working guide for translators and dashboard developers lives next to the code in [`dashboard/I18N.md`](../dashboard/I18N.md). It covers the locale registry, the catalog format, plurals, the pseudo-locales, the checks that fail the build, and the step-by-step for adding a locale or a string. This page explains how the pieces fit across the whole product and what is not translated.

## Languages

English is the source and the fallback. Spanish, Brazilian Portuguese, French, Italian, German, Simplified Chinese, Arabic (right to left), Russian, Malay, Hindi, and Japanese ship as machine-seeded catalogs, each marked beta in the language selector until a native speaker reviews it. Two pseudo-locales help catch layout bugs: `en-XA` stretches and accents every string, and `ar-XB` flips the page right to left. Select either with `?lang=en-XA` or `?lang=ar-XB`.

The chosen language is stored in the browser (`hugo.locale`), survives sign-in and sign-out, and sets `lang` and `dir` on the page. Users also have a `preferredLocale` field (`PUT /v1.0/api/users/me`) so the choice can follow them; the server stores it but does not use it to translate anything itself.

## How server text reaches the dashboard in your language

Every error the REST API returns has an English `message` and a stable `code`, for example `PasswordChangeRequired`, `AuthorizationDenied`, or `ValidationFailed`. Validation errors add per-field codes in `fieldCodes`. Enum values travel as their names (`ReadWriteWithApproval`, `Destructive`). The dashboard translates through `errorCodes.<code>`, `common.fieldCodes.<code>`, and `enums.<group>.<value>`, and only falls back to the English message when it has no entry for a code.

Connector descriptors (setting labels and help text) are English in the server. A catalog entry under `connectors.<type>.settings.<key>.label` or `.help` replaces them in the dashboard, so built-in connectors can be localized without a server release. A plugin connector shows its own text until someone adds catalog entries for it.

If you integrate with the API from your own UI, key your messages off `code`, not `message`. The English wording can change between releases; the codes are part of the contract and are listed in [`REST_API.md`](../REST_API.md).

## What stays in English

Some text is not translated, and should not be:

- Instruction text and tool descriptions sent to models. Agent Smith's persona, the safety rules, and every connector's guidance are English templates. A tenant that wants its agent to work in another language can override the persona and connector templates at the Tenant layer; see [`PROMPTS.md`](PROMPTS.md). The model then answers in whatever language the instructions and the user use.
- Tool output. Query results, log lines, and command output are data from your systems, shown as they arrived.
- Server logs, audit descriptions, and telemetry labels, which are for operators and tooling.
- Product, protocol, and provider names, setting paths, tool names, and environment variables. The glossary in `dashboard/I18N.md` lists them.

## Contributing a translation

Start from `npm run i18n:export` in `dashboard/`, which writes every key a locale lacks to `i18n-missing/<code>.json`, translate those, and run `npm run i18n:check` and `npm test`. Keep placeholders such as `{{name}}` intact, use one term per concept from the glossary, and never introduce em-dashes or en-dashes; the check rejects them. Reviews of the existing machine-seeded catalogs are the most useful contribution right now, and the known problem spots (mixed formality in Spanish, two words for "secrets" in German) are recorded in the dashboard guide.
